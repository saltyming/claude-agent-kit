# Changelog

All notable changes to Claude Agent Kit are documented here. Format loosely based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

Version numbers track the `Version` field in `CLAUDE.md`. Most entries correspond to operating-manual revisions and accompanying MCP server changes; the two ship together.

## [10.0.0] - 2026-07-03

**Slate consolidation (breaking).** claude-agent-kit is now a rendered member of the [slate-agent-kit](https://github.com/saltyming/slate-agent-kit) family:

- **Shared MCP crates moved out.** `mcp-servers/aside` and `mcp-servers/dispatch` are removed from this repo; the single shared implementation lives in `slate-agent-kit/shared/mcp-servers` (with a new `harness-log` discovery crate) and serves Claude Code, Codex CLI, and Kimi Code CLI. `make install` / `install.sh` now build + register them via slate's `tooling/install-mcp.sh --configure-claude` (aside gets `ASIDE_HARNESS=claude` — it reads each harness's session log natively now; dispatch keeps `SLATE_AGENT_STATE_HOME=$HOME/.claude` so existing per-project task history stays addressable). `workslate` remains Claude-only and stays here; GitHub Releases ship workslate only from this version (v9.4.0 is the last full three-binary artifact set). Shared-crate additions since 9.4.0: a `claude` dispatch backend (headless `claude -p`, pinned session ids, steer via `--resume --fork-session`), `no_project_root` containment hardening, native 3-harness aside transcripts.
- **Rules are render outputs.** `CLAUDE.md` and `claude-rules/*` are rendered from `slate-agent-kit/shared` sources + `adapters/claude` inserts (the redesigned corpus: an invariant kernel with stable INV-*/GATE-* IDs, execution/delegation loop files, consolidated palette gate bindings). File names and installed paths are unchanged; every 9.4.0 HARD RULE / [OVERRIDE] is mapped in slate's `docs/coverage-matrix.md`. Do not hand-edit rendered files — edit slate's shared sources and re-render.
- **Prefs templates are rendered too** (from `slate-agent-kit/shared/prefs`, configure-time placeholders now `@@NAME@@`); the interactive `configure-aside.sh` / `configure-dispatch.sh` UX is unchanged.

## [9.4.0] - 2026-07-02

Three independent workstreams, prompted by a harness comparison against `lazycodex` (an OmO/oh-my-openagent distribution for Codex) that surfaced concrete gaps where lazycodex has real code-level mechanisms this kit only had as prompt discipline: workslate's hook installer gains an anti-self-grading Stop verify hook (installed by default, not gated behind an opt-in — see below), `dispatch`/`aside` gain automatic model-fallback retry, and `palette` gains explicit weighted scoring rubrics for three previously free-form decisions. The plan was reviewed by `aside_codex` before implementation began (per the user's explicit authorization for this planning pass); its dispatch/aside findings — a real nonce-reuse-across-fallback-attempts bug and an `AuthOrPermission` retry-worthiness error — are folded into the workstreams below rather than listed separately.

**Anti-self-grading Stop verify hook (standalone `type:"agent"` entry).** `install_hooks()` (and so `make install` / `--install-hooks`) registers a fifth hook alongside the four `type:"command"` doorbells: a `type:"agent"` Stop entry whose prompt spawns an independent verifier subagent before Claude may end a turn. The verifier reads the turn's transcript tail for completion claims (tasks finished, tests passing, builds green), spot-checks the load-bearing claims against real repository state (reads the files named, runs the tests/commands cited), and answers with the documented agent-hook response schema — `{"ok": true}` to allow, `{"ok": false, "reason": ...}` to block, with the reason fed back to Claude as its next instruction; `stop_hook_active` bounds the block to one retry per turn. `hook_is_ours` gained a second, marker-string-based check (`[workslate-task-verify]` at the start of the prompt) so reinstall replaces and uninstall removes the `prompt`-shaped entry the existing `command`-content check cannot see, and `"Stop"` joined `WS_HOOK_EVENTS` so `--uninstall-hooks` covers it.

Two load-bearing implementation facts are baked into the prompt: (1) it embeds the **`$ARGUMENTS` placeholder** — Claude Code substitutes it with the hook's input JSON (`session_id`, `transcript_path`, `stop_hook_active`, `cwd`), and that substitution is the *only* channel through which the spawned verifier learns any of those values; a prompt that merely describes the input without embedding `$ARGUMENTS` leaves the verifier unable to resolve anything and silently allows every stop. (2) The response contract is the prompt/agent-hook schema from the hooks reference — `{"ok": bool, "reason"}`, which Claude Code converts to a block internally on `ok: false` — not the command-hook `decision`/`hookSpecificOutput` output shape. The hook is deliberately workslate-independent: it judges the conversation's claims against the repo directly, and task tracking (`workslate_task_*`) stays orthogonal — the board records intent and progress; the hook audits completion claims.

**dispatch / aside — automatic model-fallback retry (`model_fallback`).** Both `dispatch_submit` and `aside_codex`/`aside_copilot` gain an optional `model_fallback: Vec<String>` — on a transient backend error, the SAME task/question retries against the next model in the chain. A new `errkind` module (duplicated per-crate, matching this codebase's existing convention for small shared utilities like `lenient.rs`) classifies failures into `RateLimited` / `QuotaOrBilling` / `ModelUnavailable` / `AuthOrPermission` / `Other`; only the first three are retry-worthy — `AuthOrPermission` was originally treated as retry-worthy but corrected during review: a fallback chain swaps models *within* one already-chosen backend/account, so an auth failure affects the whole account and would fail identically on every model in the chain. The pattern table was tuned against **real captured stderr**, not guessed: a live spike (`dispatch_submit`/`aside_codex` against deliberately invalid models) found codex's actual bad-model shape ("The 'X' model is not supported when using Codex with a ChatGPT account.") does not contain the substring "unsupported model" the original design assumed, copilot's policy-denial shape ("Access denied by policy settings") has no "unauthorized"/"403" text at all, and opencode's bad-model failure is a **completely generic, non-discriminating HTTP 500** with no text to classify — a real, documented limitation, not a bug: that failure class will always fall through to `Other` and never retry.

`dispatch`'s retry loop (`executor.rs`, `run()` split into a loop over `run_attempt()`) reuses the same task row/id for every attempt — never re-enters `insert_queued`, which would trip the one-run-per-`working_dir` guard against its own prior attempt. A real bug caught during review: the original design reused one nonce across attempts on the theory that `locate_by_nonce` "scans newest-first," but that function has no snapshot/floor exclusion and returns on the first match — a retry's `record_rollout` could transiently match a still-on-disk PRIOR attempt's already-failed rollout before its own newer one appeared. Fixed: each attempt now mints its own nonce (swapped into a copy of the prompt via the existing `render::nonce_marker`) and takes its own pre-spawn `session_snapshot()`. `store.rs` gains `model_fallback` (audit copy), `final_model`, and `fallback_history` columns plus a narrow `set_fallback_result()` addition — `finish()`'s existing signature and call sites are untouched. `dispatch_status` surfaces `final_model`/`fallback_history`/a computed `fallback_summary` string when a retry occurred. `aside`'s retry loop lives in its internal `dispatch()` helper (synchronous, unlike dispatch's detached executor) and prepends a "`[answered by fallback model X after Y failed]`" note to the response. `dispatch_steer` explicitly sets `model_fallback: None` — a resumed session stays on one model, since switching mid-resume is a materially harder problem than a fresh-attempt fallback.

Both prefs templates (`claude-agent-kit--dispatch-prefs.md.tmpl`, `claude-agent-kit--aside-prefs.md.tmpl`) and their `configure-*.sh` scripts gain a comma-separated `model_fallback` default field (aside: per-backend). `claude-agent-kit--dispatch.md` gains an explicit carve-out that a fallback retry is not a fresh-confirmation trigger under the approval gate (same task id, same already-approved scope, only the model changes), plus a "Model fallback and partial state" subsection documenting that a mid-run retry does not stash or reset files a failed attempt already wrote. `claude-agent-kit--aside.md` gains a more delicate carve-out directly inside the existing "Single question per call. No loops." cost rule — a `model_fallback` retry is one logical call that happens to make more than one subprocess attempt, not the speculative/duplicate-question loop that rule targets. A separate, explicitly-optional recommendation was also added to `dispatch.md`: once a fallback chain exists, proactive-dispatch step size/duration can be somewhat less conservative about transient-failure risk specifically — it does not loosen any judgment-based exclusion (ambiguous scope, overlapping edits, tasks needing interactive judgment).

**palette — weighted scoring rubrics.** Three loop decisions that were pure free-form judgment — next-slice ranking (step 2), story-boundary drawing (step 3), and review-triage priority (step 5) — gain explicit, reviewable heuristics in a new "Scoring rubrics" section of `claude-agent-kit--palette.md` (inserted between "RST house style" and "Artifact schemas"), modeled on lazycodex's `$init-deep` directory-scoring formula but framed honestly: unlike `$init-deep`'s actually-queryable file/symbol counts, palette's axes are estimated from prose by the model re-applying the same formula each time — the value is *auditability of reasoning*, not true determinism. Each rubric scores four weighted axes (1–3 each) into an 8–24 range with three tiers; (a) and (c) both reuse two pre-scoring carve-outs (**blocked** — an external dependency the item can't presently resolve; **decision-gate** — a yes/no question, not buildable work) that a numeric score would otherwise misrank. A structural fix applied throughout: (a)'s ranking is purely conversational and ephemeral, never written back to `backlog.rst`; only (c) persists the new optional `:Priority-signal:` field on a backlog item, so a critical-but-not-thin item is never silently downgraded just because it lost a slicing race against (a). Every rubric is written to **rank and surface, never decide** — none moves `:Status:`, which stays gated on user approval exactly as the loop already required. `backlog.rst`'s `:Type:` enum also gains `chore` — a pre-existing gap unrelated to the rubric work, caught while re-quoting the schema and fixed in the same edit since it was already being touched. Retroactively validated against this repo's own live `_palette/backlog.rst`: item #7 ("Cut the 9.2.0 release," mostly done, only tag+release remaining) scores highest (22/24), and the three review-triage items with external blockers or open decisions correctly route to the carve-outs instead of being scored.

**Verification.** `cargo build --workspace` and `cargo test --workspace` (90 tests: 27 aside, 38 dispatch, 25 workslate) all run clean, and the release binaries + rule files were installed live via `make install`. The `model_fallback` feature was verified against the **actual freshly-built release binaries** speaking real MCP stdio JSON-RPC (a minimal Python client), not just unit tests — an in-process unit test calling `executor::run()` directly was attempted first and found fundamentally unworkable on Unix: `spawn_child`'s `pdeath_guard` wrapping re-invokes `std::env::current_exe()`, which inside a `cargo test` binary resolves to the *test binary itself*, causing it to recursively re-run the test suite instead of spawning codex — an architectural constraint of the guard mechanism, not a bug in this feature, so the broken unit-test module was removed rather than kept. Against the real binary: a bad primary model + working fallback correctly recovered (`final_model="gpt-5.5"`, `fallback_history` recorded exactly the one discarded attempt, real response text `"ok\n"` captured); a write attempted under a read-only sandbox correctly did *not* engage the fallback chain (codex reported the block gracefully as a success, so there was no error to retry on); `aside_codex` with the same bad-model+fallback shape returned the real "test" response with the correct "`[answered by fallback model gpt-5.5 after ... failed]`" note. The Stop hook's `type:"agent"` blocking mechanism was confirmed live: a real session's completion claim contradicted by a still-failing build produced an actual block, with the verifier's specific reason injected back into the session as its next instruction. Transcript forensics from those live firings established the observable contract — every firing logs a `type:"system", subtype:"stop_hook_summary"` entry in the session `.jsonl`, and a real block surfaces as an injected `isMeta` user message beginning "Stop hook feedback:", **not** as `preventedContinuation: true` (that field stays `false` even on a genuine block, so it is the wrong success signal to watch). Two operational caveats from the same forensics: the hook-spawned verifier leaves no subagent transcript on disk (the summary entry, the injected feedback, and repo side effects are the only observables), and a long-lived session that predates a hook install showed near-instant no-op firings while a freshly started session behaved correctly — test hook changes in a fresh session.

Version bumped 9.3.0 → 9.4.0 (minor — three additive workstreams across workslate/dispatch/aside/palette; no existing tool behavior changes for a caller who doesn't use `model_fallback` or the new rubric-informed decisions. The Stop hook is the one exception: it installs by default with `make install` and adds a verifier-subagent spawn to every Stop event project-wide — an explicit, accepted cost, not silent, but not opt-in either).

## [9.3.0] - 2026-07-02

Removed workslate's buffer-staging subsystem — the tool family behind "non-trivial code changes go through workslate first." User judgment: these 8 tools (`workslate_write`, `workslate_edit`, `workslate_read`, `workslate_list`, `workslate_diff`, `workslate_apply`, `workslate_clear`, `workslate_search`) weren't pulling their weight relative to the native `Edit`/`Write`/`Read`/`Grep` tools. Investigation ahead of the removal also found the doorbell footer's buffer-list feature ("── Buffers: N staged ──") was already dead in practice — `hooks.rs` always called `render_task_footer(&tasks, task_session, &[])`, since the doorbell hook runs in a separate process from the MCP server and can never see its in-memory buffers. Task tracking (`workslate_task_*`) and team messaging (`workslate_register` / `workslate_msg_send` / `workslate_inbox_read`) are unaffected — these are cleanly separate subsystems (direct SQLite, no shared buffer state) and remain the reason to run workslate at all.

**Code (`mcp-servers/workslate`).** `src/buffer.rs` (the `EditMode`/`BufferContent`/`resolve_target`/`apply_mode` machinery, 6 param structs, 11 tests) and `src/file.rs` (`validate_path`/`is_binary`/`format_numbered_line`/`MAX_FILE_SIZE`, used solely by the removed tools) are deleted outright. `main.rs` loses the 8 tool methods, the `buffers`/`applied_buffers`/`project_root` fields and their constructor plumbing, the buffer-only helpers (`check_file_collision`, `save_buffer`, `delete_buffer`, `delete_all_buffers`, `load_buffers_from_db`), the SHA-256 hashing and diff-context helpers, the buffer-restore block in `main()`, and the dead `workslate_write`/`workslate_edit` no-session-nudge branch in `call_tool` — down to ~1000 fewer lines. `task.rs`'s `SCHEMA_SQL` drops the `buffers` table; `migrate_db`'s old "v8.3: add buffers.source_hash" migration (which would now `ALTER TABLE` a nonexistent table) is replaced with an idempotent `DROP TABLE IF EXISTS buffers`, so upgrading installations lose the orphaned table and any leftover staged content — covered by a new `migrate_drops_legacy_buffers_table` test. `render_task_footer` drops its always-empty `buffer_names` parameter and the dead rendering block; the one call site in `hooks.rs` updated to match. `Cargo.toml` drops `similar`, `sha2`, and `regex` (each was a dependency solely for the removed diff-rendering, hashing, and regex-search code). A follow-on dead-code pass (caught by `cargo check`'s unused-function warning after the removal) also deleted `lenient_opt_u32` from `lenient.rs` along with its now-orphaned test wrapper and test section — `lenient_opt_vec_string` and `lenient_opt_bool` stay, since `workslate_task_create`'s `depends_on` and `workslate_msg_send`'s `urgent` still use them.

**Docs.** `CLAUDE.md`'s Three-Phase Workflow Execute step, Undo/Revert forbidden-mechanisms bullet, and Quick Reference decision tree all drop their workslate-buffer-staging language in favor of using `Edit`/`Write` directly. `claude-agent-kit--task-execution.md` loses its entire `## Code Staging` section (including the "Workslate safety rules" subsection) plus every buffer-specific clause elsewhere in the file (Comment Discipline's chain-of-thought list, both Undo/Revert Handling subsections' tool lists and reconstruction-source lists, the Task Sessions "Buffers are shared across sessions" bullet, and the After Completion buffer-cleared checklist item). `claude-agent-kit--parallel-work.md`'s "Code staging inside a workflow" section drops the now-inapplicable "workslate staging discipline" framing in favor of "review the diff carefully before merging." `claude-agent-kit--palette.md` drops "staging/" from its inner-loop description, the "workslate buffer" clause from its primitives list, and "+ buffer staging" from the combined-loop ASCII diagram. `claude-agent-kit--aside.md`'s two off-disk-data examples ("a staged workslate buffer that is not yet applied") are reworded to the general case. `README.md`'s workslate summary, honest-caveat paragraph, CLAUDE.md-section description, and dedicated `### workslate MCP server` section are all trimmed to task-tracking + messaging only.

**Breaking change.** This removes 8 tools from workslate's MCP surface. Any saved workflow, skill, or muscle-memory habit that calls `workslate_write`/`workslate_edit`/`workslate_read`/`workslate_list`/`workslate_diff`/`workslate_apply`/`workslate_clear`/`workslate_search` directly will fail after upgrading — use `Edit`/`Write`/`Read`/`Grep` instead.

**Verification.** `cargo check -p workslate`, `cargo build -p workslate`, and `cargo test -p workslate` (23 tests, all passing, including the new migration test) all run clean; `cargo fmt --check -p workslate` and `cargo clippy -p workslate --all-targets` are clean with zero warnings. A repo-wide grep for the removed tool names across `claude-rules/`, `CLAUDE.md`, `README.md`, and `mcp-servers/workslate/src/` returns zero hits outside this changelog entry's own historical record. Not yet built/installed live — `make install` (which rebuilds the binary and copies the rule files to `~/.claude/`) is a separate, proposed step.

Version bumped 9.2.0 → 9.3.0 (minor — removal of workslate's buffer-staging tool surface, with accompanying doc cleanup across `CLAUDE.md` and five `claude-rules/` files).

## [9.2.0] - 2026-07-01

Four workstreams: OpenCode arrives as `dispatch`'s second backend (its first CHANGELOG entry — the integration had accumulated across prior uncommitted sessions without ever being released), a rules-doc duplication cleanup, an audit of every `[OVERRIDE]` block's quoted system-prompt text against the *current* session's actual system prompt (not the "4.7" prompt two prior self-corrections targeted), and **palette**, a new product-intent outer loop layered onto the existing inner loop (its own section below). The OpenCode work is code + docs, delegated to `dispatch`'s own codex backend and independently reviewed; the other two are docs-only.

**palette — a product-intent outer loop.** A new always-loaded capability that wraps the framework's existing *inner* loop (Three-Phase Workflow + workslate + dispatch) with a *strategic outer loop*: a durable RST backlog of product intent → thin-slice a phase with the user → hand a story's acceptance criteria to the inner loop at the existing "Get approval" gate → review and re-plan on completion, harvesting back into the backlog. It fills the gap that everything the framework had was within-task and evaporated at the task boundary — there was no durable, cross-session record of *what we are building and why*, and no re-planning cadence.

- **Folder-gated engagement.** The trigger is a `_palette/` directory: present → the agent weaves the outer loop into its normal work automatically (always-on *within an opted-in project*); absent → fully dormant, except a one-line offer to run `palette-init` on genuinely roadmap-shaped work. Opt-in is explicit (`palette-init`); palette never scaffolds a project unasked. Auto-engagement ≠ auto-authority — the folder switches on the *advisory* loop, not execution rights.
- **Tier A / Tier B authority firewall.** To stop a new intent ledger from silently becoming a second definition of "current scope," the split is strict: the backlog/phase/story artifacts are **advisory** (they *propose* scope, never authorize an edit — "an intent ledger, not an execution authority"), while the existing approval gate + workslate/dispatch stay **binding**. A two-directional scope invariant forbids palette from shrinking requested scope *or* moving unmet acceptance criteria into the backlog at completion time without specific user consent; deviations reuse the existing `Forced Spec/Plan Deviation` gate (a story's `Done when` + `Not this story` are its "approved spec").
- **Rule + skills.** New always-loaded rule `claude-rules/claude-agent-kit--palette.md` carries the loop, the firewall, and the RST artifact schemas **inline** (backlog / phase-brief / story / index / reviews) — inline rather than a lazily-read reference file, because an agent reading files under `~/.claude/` at runtime is a security-audit smell (the normal path is the harness loading rules, not the agent reading them). Five lazy-loaded skills under `claude-skills/`: `palette-init` (opt-in scaffold + light intake + a `_palette/.gitignore` prompt) and four **pull-only** design-artifact helpers (`palette-spec` / `palette-ux` / `palette-ui` / `palette-rules`) that are never part of the default loop.
- **RST as robust-subset structured text.** Artifacts are text the agent reads back, not Sphinx-rendered docs, so the house style is a deliberately small subset (field lists, plain bullets, literal `- [ ]`, simple underlines; no `list-table`, no nested directives) that LLMs do not silently malform.
- **Woven into the manual, not bolted on.** Integration pointers were added where the current loop is described: `CLAUDE.md` (a Three-Phase Workflow note, a Decision-Tree branch, and a "Get approval = hand-off" marker), `task-execution.md` (four notes — at the task-tracking trigger, the complete-the-scope override, the post-inspection-deferral gate, and the forced-deviation gate), `parallel-work.md` (delegate the *approved* scope, never the raw story), plus secondary notes in `git-workflow.md` and `dispatch.md`. `_palette/` defaults to **not committed** (a personal planning record; `palette-init` offers a `.gitignore`).
- **Install.** `Makefile`, `install.sh`, and `install.ps1` gained directory-shaped skill install/uninstall for `claude-skills/palette-*` — manifest-tracked, and removed on uninstall only after verifying the `<!-- claude-agent-kit -->` signature inside each `SKILL.md` (skills carry the signature in the body, since a skill's YAML frontmatter must be the first line). `install.sh`'s hardcoded rule-file list also gained the previously-missing `claude-agent-kit--palette.md`.
- **Verification (palette).** `make -n install` parses cleanly and `sh -n install.sh` passes; the Makefile/install.sh skill blocks were tab- and syntax-checked. `install.ps1` could **not** be syntax-checked locally (no PowerShell on the dev machine) — its edits follow the existing patterns but need a Windows check. A codex review of the finished implementation caught and fixed a real `install.ps1` uninstall-ordering bug (skill *directories* fell into the file-only removal path and, under `$ErrorActionPreference = "Stop"`, would abort uninstall before the signed dir-cleanup ran — the generic pass is now `-PathType Leaf` so dirs fall through to the signed cleanup, matching `install.sh`'s `[ -f ]`), plus two firewall-wording tightenings in `palette.md` (story acceptance criteria are the "approved spec" only *after* the hand-off gate; **all** `_palette/` artifacts, including the optional tech-spec/UX/design/rules ones, are Tier A / advisory) and quoting of the Makefile skill-copy paths. As with the rest of this entry, palette is **not yet built/installed or live-exercised**: no `make install`, and no end-to-end `palette-init` → slice → hand-off → review run against a real project. Highest-risk areas to verify live: folder-gated dormancy (a non-palette project stays untouched) and the completion-time scope firewall (unmet acceptance criteria are never silently deferred).

**OpenCode backend — what's new, and how it differs from codex.** `backend.rs` gains a `Backend::Opencode` variant alongside `Backend::Codex` (`all()` / `parse()` / `binary()` / `install_hint()` all branch on it; the codex-only `build_command` match arm gets an `unreachable!("opencode dispatch uses the server API runner")` guard, since OpenCode never goes through that spawn path). Architecturally the two backends work differently: codex is a one-shot CLI subprocess dispatch spawns and captures stdout/stderr from, whereas OpenCode is driven through a short-lived local `opencode serve` HTTP server — dispatch spawns it, creates a session and submits the prompt over its REST API, then reads its `/event` SSE stream for live progress. The new `mcp-servers/dispatch/src/opencode.rs` module owns this (Cargo.toml gains `reqwest` and `futures-util` as dependencies for the HTTP/SSE client); `executor.rs`'s `Job` struct gained two OpenCode-specific fields (`state_dir` for the server's working state, `rollout_path` for steer/resume continuity) and now branches to `opencode::run()` when `job.backend == Backend::Opencode`, sharing a new `finish_outcome()` helper with the codex path so both write the same terminal-status/result shape to the store. `model` accepts OpenCode's `provider/model` form (parsed by `parse_provider_model`) where codex takes a flat model id; `reasoning_effort` maps to OpenCode's `variant` field where codex passes `-c model_reasoning_effort=`. The `dispatch_logs` a caller sees is normalized JSONL either way — OpenCode's real event stream (`message.part.updated`/`message.part.delta` with a `part.type` discriminant across text/reasoning/tool/step-start/step-finish parts) is normalized into the same line shape codex's rollout produces, with the native OpenCode event preserved per-line under `"native"` for debugging. Version probing (`dispatch_backends`, and the version recorded per task for audit) now probes every `Backend::all()` entry at boot instead of hardcoding codex, so the `Dispatch` struct's `backend_version: Option<String>` became `backend_versions: HashMap<String, Option<String>>`. Installer/config wiring — `scripts/configure-dispatch.sh`, `install.ps1`, and `claude-agent-kit--dispatch-prefs.md.tmpl` — gained a `DISPATCH_BACKEND` prompt/env var (`codex` default, validated against `codex|opencode`) alongside the existing policy/approval/model/effort prompts, with the model/effort prompt text reworded to cover both backends' conventions. `render.rs` and `store.rs` got doc-comment wording generalized from "codex" to "backend" to match (no behavior change).

**Event-mapping bug caught before this backend ever shipped.** While wiring up backend-aware reasoning defaults (below), `normalize_event`'s dispatch table turned out to match SSE event-type strings (`session.next.tool.called`, `session.next.text.ended`, `session.next.reasoning.*`) that do not exist anywhere in the real OpenCode API — confirmed against the installed CLI's actual OpenAPI spec and TypeScript SDK type definitions (real content-bearing events are `message.part.updated`/`message.part.delta`; a repo-wide grep of the installed SDK for "session.next" returned zero matches). Caught and fixed in this same delivery, before OpenCode support was ever released: `normalize_event` now dispatches on real `message.part.updated` events (`part.type` "text"/"reasoning"/"tool", with tool's `state.status` driving running/completed/error rendering) and ignores `message.part.delta`; repeated `message.part.updated` events for the same part (text/reasoning parts have no explicit "finished" signal, unlike tool's `state.status`) no longer produce duplicate/growing lines — `rollout::curate()` now tracks the latest rendered line per `partID` and replaces rather than appends.

**Reasoning-by-default (the original ask).** OpenCode exposes plaintext reasoning text, unlike codex whose reasoning is API-encrypted, so `rollout::default_kinds()` is now backend-aware: `lifecycle, messages, tools, edits` for codex/unknown, plus `reasoning` for opencode. `render()` emits the real extracted reasoning text when present, falling back to the existing opaque `[thinking] (reasoning)` placeholder for codex exactly as before. `params.rs`, `claude-agent-kit--dispatch.md`, and `README.md` describe the per-backend default split; `opencode.rs`'s existing unit tests (previously written against the fabricated event names) were rewritten against real fixtures, and new tests cover tool terminal states, reasoning text extraction, backend-aware defaults, and the per-`partID` dedup behavior.

**Cross-platform process-orphaning fix.** Live-testing the OpenCode backend above surfaced a further, more serious bug: closing Claude Code while a `dispatch` task is running left the backend child (`opencode serve`, or codex) running unsupervised in the background, continuing write-capable agentic work with no user visibility and no way to stop it short of finding and killing the process manually. Root cause: `spawn_child`/`spawn_server` put the backend in its own Unix process group (`process_group(0)`) so `dispatch_cancel` can `kill(-pgid, …)` the whole subtree without taking down the dispatch server itself — but that same isolation is exactly what prevents any signal from reaching the child when dispatch's own process dies (most likely via a hard `SIGKILL` from Claude Code's process teardown). `main.rs::main()` had zero shutdown handling. Two adjacent, pre-existing bugs were found and fixed in the same delivery: `kill_process_group` was a no-op stub on non-Unix, so even the *existing* `dispatch_cancel` never killed descendants on Windows; and `process_alive` unconditionally returned `true` on non-Unix, so the existing boot-time `reconcile()` backstop never marked an orphaned Windows row `interrupted`.

The fix is platform-native rather than one-size-fits-all, since no single primitive covers all three targets: **Linux and macOS** each gained a new `pdeath_guard` module — a hidden `dispatch __pdeath_guard <dispatch_pid> -- <argv...>` re-invocation of the same binary that sits between dispatch and the real backend, becomes the pgid leader in its place, and reacts to parent death by killing the whole group. A bare `PR_SET_PDEATHSIG` directly on the backend was considered and rejected: it only arms the one process that calls it, not a descendant the backend spawns mid-run, which would leave a real parity gap against the group-kill `dispatch_cancel` already provides. Linux detects parent death via `PR_SET_PDEATHSIG` delivered through a `signalfd` (passive, kernel-pushed, arm-then-recheck-liveness ordering to close the fork/exec race); macOS, which has no passive equivalent, uses `kqueue`/`EVFILT_PROC`/`NOTE_EXIT` with one blocking `kevent()` watching both the parent and child pids, EINTR-retried, and prioritizing parent-death cleanup over a same-batch child-exit event. The guard is deliberately synchronous with no Tokio runtime — `main.rs`'s entrypoint now argv-sniffs for `__pdeath_guard` before booting Tokio at all, the single highest-blast-radius change in the delivery since it touches the normal boot path on every platform. **Windows** needed no guard: a new `winjob` module assigns the child directly to a `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` Job Object (via `Child::raw_handle()`), which the kernel itself tears down when the job handle's last reference closes — no process needs to stay alive to react. Job Object setup failure is treated as fatal (kill the child, fail the spawn) rather than silently continuing without protection, an explicit user-confirmed decision. A cross-platform `tokio::signal`-based graceful-shutdown path (Ctrl+C, plus SIGTERM on Unix) was also added as defense-in-depth for the interceptable-termination case; it does nothing for a hard `SIGKILL`, which the native per-platform mechanisms above exist specifically to cover.

## [9.0.0] - 2026-06-26

New `dispatch` MCP server — a third delegation surface. Where `aside` asks another model family for a read-only second opinion (horizontal consultation), `dispatch` hands an execution *step* to an external coding agent (codex) running as a headless, write-capable subprocess (hierarchical delegation). Adds `mcp-servers/dispatch/` (Rust, rmcp), a new rule file, a user-owned prefs file, and the `CLAUDE.md` / `README` / build-script wiring. Design pressure-tested with `aside_codex` (gpt-5.5 / xhigh) and built-in `advisor()`; the MCP-protocol paths (boot, tools/list, backends probe, every input guard) and the unit tests (cross-connection concurrency guard, rollout curation/paging) were verified in-session, and the full codex round-trip — submit → run → `succeeded`, a live curated log tail while `running`, and session-resume steering — was verified end-to-end against real codex. Propagates on next `make install`.

**The server (`mcp-servers/dispatch`).** Eight tools: `dispatch_submit` (delegate one step; returns a task id immediately and runs detached — MCP is request/response but a delegated run takes minutes, so the model is submit → poll/wait → cancel), `dispatch_status`, `dispatch_wait` (a **bounded** long-poll — block until the task is terminal or `timeout_ms` elapses, default 30s / cap 120s, returning `timed_out`; deliberately never an unbounded hold that would hit the MCP request timeout), `dispatch_list`, `dispatch_cancel` (by id or by whole `plan_id`), `dispatch_logs`, `dispatch_steer`, and `dispatch_backends`. Tool rejections return a **structured** `{error:{code,message}}` with a stable code (`working_dir_outside_root`, `sandbox_forbidden`, `dir_busy`, `session_not_ready`, …) rather than free text. codex runs `codex exec -C <working_dir> -s workspace-write -a never [--skip-git-repo-check] [-m …] [-c model_reasoning_effort=…]` with the rendered prompt on stdin (`-C` sets the working root explicitly and records it in argv). Task state persists in its own SQLite `dispatch.db` (separate from `workslate.db`, same project-anchored path convention; WAL + busy_timeout). A `Backend` enum is the single extension seam for future agents. `dispatch_submit` takes a structured spec (objective / target_files / constraints / acceptance) plus free-form context/details, rendered deterministically into the codex prompt and stored alongside it for audit.

**Async + correctness.** A detached tokio task per submit owns the run and registers a cancellation token in an in-memory registry; the row goes `queued` → `running` only after the child spawns (so cancel/status never race a row with no pid), stdout/stderr are captured into size caps *during* streaming (not buffered unbounded into memory/SQLite), and cancel kills the backend's whole process group (codex + any shells/test runners it spawned) while it is still live and before reaping it, so the group signal can never hit a reused pgid — not just the direct child. Boot reconciliation marks stranded `running` rows `interrupted` only when their owner process is dead (`kill(pid,0)` liveness on unix), so a peer session's live tasks are never clobbered.

**Live logs + steering — supervisable, not fire-and-forget.** `dispatch_logs` reads codex's own session rollout (JSONL under `$CODEX_HOME/sessions/…`, located by the run's own identity — see *Rollout association* below) and renders a **curated** timeline — user/codex messages, tool calls, file edits, lifecycle — dropping the noise (the giant system prompt, token counts, encrypted reasoning, duplicate developer messages); it works while the run is live and is **line-range paged** (default tail, byte-capped) so a long session can't blow the MCP output budget. `dispatch_steer(id, instruction)` **interrupts** a run (cancelling it if active) and **resumes the same codex session** (`codex exec resume <session_id>`, the id captured from the rollout) with a new instruction — the accumulated context and the files codex already wrote are preserved — recorded as a new `parent_id`-linked task so the turn history shows in `dispatch_list`. This is the "watch → interrupt → redirect" loop the sub-agent model implies; steering is at *turn* granularity (codex `exec` takes no mid-turn injection — you stop and resume). New `rollout.rs` module + columns `session_id` / `rollout_path` / `parent_id` / `nonce` / `rollout_start_line` (idempotent ALTER migration).

**Rollout association — positive identity, not cwd-guessing (correctness fix, caught in-session).** The first cut located a task's rollout by *the newest rollout whose `session_meta.cwd` matches the working_dir* — but `aside` (the sibling server) also runs codex and, inheriting the project-root cwd, writes rollouts into the same `$CODEX_HOME/sessions/`. So `dispatch_logs` could surface a **prior aside session's** log, and a poisoned `session_id` could make `dispatch_steer` resume an **unrelated** codex session write-capable. Fixed by associating on **independent identity**: `dispatch_submit` injects a per-task **nonce** into the rendered prompt (codex records it verbatim in an early `user_message`), and a fresh run is matched **only** by that nonce — never a cwd guess, so it fails closed until its own rollout is written; a **steered** run is matched by the inherited, authoritative `session_id` (filename-exact) and records its identity at steer time, closing the window before the executor would otherwise record it; a **legacy** row (no nonce) is gated by cwd **plus** a not-older-than-start time floor (`parse_sqlite_utc`, a chrono-free days-from-civil parser), which breaks the circular `session_id == session_id` self-check on an already-poisoned row. `resolve_rollout` / `resolve_session_id` validate a cached path against that same identity before trusting it and **fail closed** otherwise (`session_pending`, never a re-guess by cwd). Bundled refinements: `dispatch_logs` slices a steered task's log from its `rollout_start_line` so it shows only the new turn; `dispatch_steer` echoes the inherited sandbox/model/effort; `read_session_meta` falls back `session_id`→`id` for older codex logs. codex CLI has **no** caller-supplied session-id pinning (verified on 0.142.0), so identity rides in-band via the nonce rather than a flag (`codex exec --json` is recorded as the future authoritative-session-id path). New unit tests cover snapshot / nonce / session-id locating and the date parser; pressure-tested across two `aside_codex` (gpt-5.5 / xhigh) review rounds + `advisor()`, which caught the legacy-circularity and steer-window defects now fixed.

## [8.8] - 2026-06-16

First release that ships MCP server code, hook scripts, and install-script changes together with the rule docs (recent entries were docs-only). Adds a **team-messaging + per-tool-call steering layer to workslate** so an Agent Teams leader can redirect a running teammate before its current turn ends — closing the long-standing gap where a message to a busy teammate is only delivered at the next turn boundary, by which point it may have completed work in the wrong direction.

**Mechanism.** Claude Code's `PreToolUse` hook supports `hookSpecificOutput.additionalContext` (verified against the installed binary; injected independently of `permissionDecision`, so a hook can allow the tool *and* inject context — a non-blocking side channel) and fires inside Agent-Team teammates (the team inherits the lead's hook config). workslate exploits this with two wildcard `PreToolUse` "doorbell" hooks that run on every tool call: a **task-status** doorbell and a **team-inbox** doorbell. Each is a subcommand of the workslate binary (`workslate --hook=task` / `--hook=inbox`) that reads the hook-input JSON from stdin, resolves the calling Claude session to its task session + role, queries the DB, and prints an `additionalContext` object. stdout is strictly the hook JSON; any error logs to stderr and injects nothing — a doorbell never blocks a tool call.

**Identity & durability.** Messages are addressed by the durable **role name** (the existing `owner` concept), not by the ephemeral session id, so a respawned teammate of the same role still receives messages.
